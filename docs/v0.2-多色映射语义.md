# ams_mapping 的语义：已知、未知、怎么定

> 本文件是 v0.2 多色打印相关**实测结论的唯一落点**。与社区文档冲突时以这里为准
> ——这个项目已经被「社区文档与实测相反」坑过两次（FTPS 数据通道必须加密、
> `plate_N.gcode` 不一定是 `plate_1`）。
>
> 状态：**取证进行中**。下面标 ⬜ 的是还没定的，标 ✅ 的是已经有证据的。

## 为什么这件事值得专门开一个文件

`project_file` 指令里的 `ams_mapping` 是一个整数数组。猜错的后果不是报错——
**是打印机照单全收、用错料、且全程不报错**。等发现的时候件已经打废了。

v0.1 只验证过单色的 `[0]`，多色的三个语义全是未知量。

## 三个未知量

### ⬜ 1. 数组长度：按「该盘用到的耗材数」还是「项目全局槽位数」？

这决定了 `threemf.match_ams()` 该产出多长的数组。

**已有证据（来自 `assets/studio_reference.gcode.3mf`，单色，用 `scripts/05_dump_3mf.py` dump）：**

| 来源 | 值 | 编号基准 |
|---|---|---|
| `Metadata/slice_info.config` 的 `<filament id=...>` | `id="1"` | **1-based** |
| `Metadata/plate_3.json` 的 `filament_ids` | `[0]` | **0-based** |
| `Metadata/plate_3.json` 的 `filament_colors` | `["#FF671F"]` | — |
| `Metadata/filament_sequence.json` 的 `plate_3` | `{"sequence": [1], "optimal_assignment": [0,0], "nozzle_sequence": [0]}` | 混用 |
| `slice_info.config` 的 `filament_maps` | `"1 1"` | — |

✅ **已确认**：`slice_info.config` 的 filament id 是 **1-based**，而 `plate_N.json`
的 `filament_ids` 是 **0-based** 的槽位索引。两者相差 1，这是最容易写错的地方。

⬜ **待确认**：单色样本里两个数组长度都是 1，看不出差别。**需要一个「项目里配了 3 卷料、
但某个盘只用其中第 1 和第 3 卷」的 3mf** 才能分辨——那时若 `filament_ids` 是 `[0,2]`
而 `slice_info` 里是 `id=1, id=3`，就说明 `ams_mapping` 必须按全局槽位补齐成
`[t1, 哨兵, t3]` 而不是密集排成 `[t1, t3]`。

> 注意 `optimal_assignment: [0,0]` 长度是 2 而这个盘只有 1 种耗材——猜测与双喷嘴
> 机型有关（A1 是单喷嘴），暂不作为依据。

### ⬜ 2. 下标对齐：`ams_mapping[i]` 对应第 i 号还是第 i+1 号耗材？

当前实现按「`ams_mapping[i]` 对应 filament id == i+1」（即 slice_info 的 1-based id）。
这与 `plate_N.json` 的 0-based `filament_ids` 自洽，但**没有直接证据**。

### ⬜ 3. 不使用 AMS 的那一位填 `-1` 还是 `255`？

社区实现两种都见过。已做成配置项 `[print] external_spool_id`，**实测后改一行配置即可，
不用改代码**。

## 取证手段

### ✅ 已排除：从 Bambu Studio 日志里捞

Studio 的日志（`%APPDATA%/BambuStudio/log/studio_*_enc_cn.log.0`）是 **AES 加密**的：
只有一段明文 header（含 `enc_block_size: 16`、`enc_key_tag`），正文可打印字符仅 43%，
`grep project_file` 零命中。**这条路不通，别在上面浪费时间。**

### 手段 A：`scripts/05_dump_3mf.py`（零风险、零真机）

在 Studio 里切一个多色 3mf——**最好是「项目配 3 卷料、某个盘只用第 1 和第 3 卷」**，
这样能一次回答未知量 1 和 2：

```bash
python scripts/05_dump_3mf.py path/to/multicolor.gcode.3mf
```

把输出贴回本文件的「实测记录」一节。

### 手段 B：`scripts/06_mqtt_relay.py`（有风险，尚未实现）

起一个本机 TLS 中继假扮打印机，让 Studio 连上来，抓它自己发的 `project_file` 原始
payload。这是最权威的答案，但要自己写一个极简 MQTT broker，且 Studio 可能有额外校验。
**仅在手段 A 无法定论时才做。**

### 手段 C：真机二分试错（P8 集中验证时）

最省耗材的验法：提交一个多色任务，触发时刻设 1 分钟后，**到点立刻在打印机面板取消**，
只看 report 里的 `ams.tray_tar` 是否指向期望的槽位。不用真打完。
外部料哨兵先发 `-1`，被拒再改 `255`。

## 当前进度与待办（2026-08-25 归档）

多色打印按用户要求**暂时搁置**，等后续版本跟进。这里记下停在哪一步，
免得下次捡起来时又要重新推一遍。

### 已经做完的

- ✅ **`match_ams` 的索引错位已修并测试**（`tests/test_match_ams_multicolor.py`，17 个用例）。
  改成按 filament id 定位下标，该盘没用到的位置填 `external_id` 占位。
  修之前是密集 append：盘只用了项目里 1 号和 3 号耗材时会得到 `[ta, tc]`，
  把 3 号的托盘放到 2 号的位置上，**打印机照单全收、用错料、且不报错**。
- ✅ 外部料哨兵做成了配置项 `[print] external_spool_id`（默认 -1），
  数组长度做成了 `match_ams(..., slot_count=)` 参数。实测之后改一行即可。
- ✅ WebUI 的映射编辑器能显示多个耗材、逐个选槽位、人工覆盖后标记 `manual`。
- ✅ 编号基准已实测确认：`slice_info.config` 的 filament id 是 **1-based**，
  `plate_N.json` 的 `filament_ids` 是 **0-based**，两者差 1。

### 还差的（都需要真机或一个多色 3mf）

1. ⬜ **外部料哨兵到底是 -1 还是 255。** 最省耗材的验法：提交一个含外部料位的
   多色任务，触发时刻设 1 分钟后，到点立刻在打印机面板取消，只看 report 里的
   `ams.tray_tar` 是否指向期望槽位。被拒就把 `external_spool_id` 改成 255 重试。
2. ⬜ **数组长度按「本盘用到的耗材数」还是「项目全局槽位数」。**
   需要一个「项目配 3 卷料、某个盘只用第 1 和第 3 卷」的 3mf，
   跑 `scripts/05_dump_3mf.py` 对比 `plate_N.json` 的 `filament_ids`
   与 `slice_info.config` 里 `<filament id=...>` 的集合。
3. ⬜ **多色实打一次**，确认换色顺序和颜色都对得上。
