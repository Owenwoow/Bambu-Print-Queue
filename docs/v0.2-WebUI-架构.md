# v0.2：WebUI 与连接架构

> 这份文档解释 v0.2 的几个不显然的决定，以及它们各自在防什么。
> 与实测结论相关的部分以 [`验证记录-通道A.md`](验证记录-通道A.md) 为准。

## 一切的起点：打印机只接受一个 MQTT 连接

这条硬约束决定了 v0.2 的几乎所有架构选择。

v0.1 里它没造成麻烦——CLI 用完就断，daemon 也用完就断，撞不上。但 WebUI 要显示
实时状态，就必须常连；一旦常连，那条连接就从「随手可得的资源」变成了**稀缺资源**，
必须有一个明确的主人，否则会重现 v0.1 验收时踩过的事故：两个客户端互相踢线，
定时任务到点读到 `UNKNOWN`，打印机明明空闲着却被放弃。

于是有了三条规矩：

1. **WebUI 寄生在 daemon 进程里**，不是独立服务。独立进程要么另开连接（把 daemon
   踢下线），要么自己造一层 IPC 代理（成本远高于塞进来）。所以
   **一个 daemon = 一条连接 = 一个 web 服务**，daemon 那把单实例文件锁顺带成了
   WebUI 的端口守卫。
2. **daemon 里任何代码都不许再调 `build_transport()`**，一律找 `PrinterLink` 借。
3. **别的进程要数据就走 HTTP**。CLI 因此改成了「daemon 在就问它，不在才自己连」。

## 进程内的样子

```
bpq daemon（一个进程）
├── single_instance(var/bpq.lock)      ← 抢不到就拒绝启动
├── keep_awake()                        ← 运行期间阻止系统睡眠
├── TaskStore                           ← 打开时触发 schema 迁移
├── PrinterLink ─────────────► 打印机   ← 唯一的一条 MQTT 长连接
│     └── ReportAccumulator             ← 增量报文合并成完整快照
├── TaskRunner(transport=link.session)  ← 借连接，用完不关
├── BackgroundScheduler（后台线程）      ← 到点调 run_task
├── uvicorn（后台线程）                  ← FastAPI：REST + SSE
└── 主线程 stop.wait()                  ← 留着第一时间响应 Ctrl-C
```

关停是反序的：先摘掉运行时注册表（别让触发中的 job 摸到正在拆的对象），
再停 web、停调度、断连接、关库。

**绝不给 uvicorn 开 `reload`**：它会 fork 出 reloader 子进程，那会让单实例文件锁
失去意义——两个进程同时以为自己独占。开发前端用 `npm run dev`，改后端就手动重启。

### 到点触发为什么要走运行时注册表

APScheduler 的 job 存在 jobstore 里的只是一个字符串 `"bpq.daemon:run_task"`，
到点时以模块级函数的方式被调用，拿不到 daemon 里那些活的对象。v0.1 靠
`run_task` 自己 `load_config()` + 新建连接来绕过——但在有长连接的前提下，
那等于 daemon 每次触发都把自己踢下线。

所以有了 `runtime.py`：daemon 启动时把自己登记进去，`run_task` 先查一下，
查到就复用现成的 runner 和连接。做成模块级单例而不是往 job 的 args 里塞对象，
是因为 jobstore 要序列化 args，而活的连接和数据库句柄根本序列化不了。

## 让出连接

WebUI 顶栏那个「让给 Studio」调 `link.yield_connection()`，断开 MQTT。
daemon 继续跑，定时任务照常在册。

**关键在于到点必须能抢回来。** `TaskRunner.fire()` 开头无条件调
`resume_connection()`，真的从让出状态抢回来了还会往 journal 记一条
`connection_reclaimed`——免得事后看到「Studio 突然断了」不知道为什么。

没有这一步的话，「让出连接」就成了一个能让定时任务静默失灵的开关。
这是 v0.2 里最容易造成事故的地方，所以它在真机验证清单里单列一项。

## 实时推送：为什么是 SSE

- 需求是**单向**的（打印机 → 浏览器），所有写操作走 REST。WebSocket 的双向能力
  在这里是纯负担。
- `EventSource` 自带断线重连。
- 不需要额外依赖（uvicorn 装的是不带 `[standard]` 的精简版，因为不需要
  `websockets`，也不开 reload 所以不需要 `watchfiles`）。
- 能直接 `curl -N http://.../api/events` 肉眼调试——在只有假打印机的开发阶段
  这条很值钱。

唯一的代价：`EventSource` 不能自定义请求头，所以用不了 `Authorization: Bearer`。
这恰好和 Cookie 鉴权吻合，也顺带避免了把口令塞进 URL query。

### 协议

```
event: snapshot   连上永远先发一条完整快照，前端整体替换 state
event: patch      RFC 7386 merge patch，前端深合并；数组整段替换不做元素级 diff
event: tasks      任务列表（整个数组）
event: journal    一条刚写入的日志
event: resync     队列溢出，让客户端重新对齐
: keepalive       每 15 秒一行注释，穿透中间代理的空闲超时
```

响应头必须带 `Cache-Control: no-cache` 和 `X-Accel-Buffering: no`，
否则中间的代理（含 Vite 的 dev server）会把事件攒着不发，界面看起来像是死的。

### 两条跨线程边界

状态变化产生在 paho 的接收线程和 APScheduler 的 worker 线程，而 SSE 的消费者在
asyncio 事件循环里。`EventBroker` 是唯一的交汇处，投递一律走
`loop.call_soon_threadsafe`。

每个订阅者一个 `maxsize=64` 的队列。**一个卡住的浏览器绝不能把打印机的状态流
一起拖停**——队列满了就清空积压、压一条 `resync` 让它重新对齐，生产端永不阻塞。

### 任务状态为什么挂在 Journal 上推

到点触发是 APScheduler 在后台线程里干的，**不经过任何 HTTP 路由**。
只在路由里推送的话，任务真的开打了网页上还显示「已就位」，得手动刷新——
而「到点了到底打起来没有」恰恰是这个应用最该实时告诉人的一件事。

任务的每一次状态流转都会写一条 journal，那是所有变化的必经之路，
比在 runner 里逐个调用点埋钩子更难漏。

## 鉴权

一个共享口令 + 无状态 HMAC 签名 Cookie + 本机免鉴权。不引入用户系统，标准库做完。

| 决定 | 为什么 | 代价 |
|---|---|---|
| 无状态签名，不是内存 session | daemon 重启后浏览器不用重登。跑在家里的东西会因为各种原因重启 | 签发出去的 token 在过期前无法单独吊销 |
| 口令指纹进签名 | 改口令 = 所有设备立即登出。这个副作用是想要的 | — |
| 本机免鉴权（默认开） | CLI 零配置走 HTTP | **这台电脑上任何进程/用户都能操作打印任务**。多人共用要关掉 |
| 不设 Secure cookie | 局域网是 http，设了浏览器就不带 cookie | **口令明文过局域网**，别复用别处的口令 |
| 登录失败限流 | 局域网里一个八位口令是纸糊的 | — |

**绑到非回环地址却没设口令时，daemon 拒绝启动 web**（本体照常跑，定时任务不受影响）。
这是防「随手把打印机控制权暴露到内网」的最后一道闸。

明确不做：用户表、注册、找回密码、OAuth、自签 HTTPS。想要 TLS 的自己套反代。

## 前端

React + Vite + Tailwind，深色底配拓竹绿。产物 `web/dist` **不入库**——
构建产物进 git 会让每次改前端都拖一堆 diff。代价由「未构建时返回一页构建说明
而不是 404」兜住。

三处界面上的坚持，每一处都在防一种具体的误解：

1. **五个打印开关是三态，不是开关。** `null`（跟随全局）和 `false`（这一单就是不要）
   是两回事：前者会跟着 `config.toml` 变。界面照实显示「跟随全局（当前：关）」，
   折叠成「关」会让人以为这一单显式关过。
2. **「本次将下发」和「设备当前设置」分区显示，不做对照。** 见下表。
3. **顶栏两个分开的指示灯**：浏览器↔服务、服务↔打印机。混成一个会让排障变成猜谜。
   AMS 卡片下固定写着「型号和颜色是在 Studio 里手填的」——自动配料的一切判断
   都建立在这两个值上，看的人有权知道它们的来路。

### 那五个开关，到底哪些能读回来

| Studio 对话框开关 | 下发字段 | 能否从 report 读回 |
|---|---|---|
| 延时摄影 | `timelapse` | **部分**。`ipcam.timelapse` 是设备侧持久设置，语义相近但不等同于「本次是否录」。⚠ 下发是否翻转它待真机确认 |
| 自动热床调平 | `bed_leveling`(+`levelling`) | **不能**。只能从 `stg_cur` 是否经过调平阶段事后推断 |
| 动态流量校准 | `flow_cali` | **不能直接读**。间接信号：校准后 `tray.k` 会变 |
| 振动补偿 | `vibration_cali` | **不能**。间接信号同上 |
| 首层检查 | `layer_inspect` | **部分**：对应 `xcam.first_layer_inspector`，但 A1 没有腔内摄像头，很可能缺失或恒 false |

五个里三个根本读不回来——这就是「我们发了什么」和「机器说了什么」必须在数据结构上
分开的原因。画成对照表就是在编造确定性。
