# 定时打印任务调度器（暂名 bpq）

## 一句话

替我记住"睡前再打"这件事的中间人。

---

## 现状与痛点

打印机在书房。启动例程（尤其是振动补偿那一段）声音大，晚上开工会吵到休息。

真正的痛点不是"我想定时"，而是 **"我不想把动作留给未来的自己"**：

有灵感的时候人在电脑前、状态在线，希望当场把事办完。但正确的做法是等到睡前离开书房时再点开始——而睡前经常忘。于是每次都变成两个坏选项二选一：现在打（吵），或者待会儿打（会忘）。

已经排除的做法：

- **"发送不启动"**（Studio 里选 Send 而非 Print）—— 没有解决问题。任务是躺在机器里了，但"到点去点一下"这个动作还是留给了睡前的自己，而那个自己会忘。
- **gcode 里插 `G4` 延时** —— 等待期间机器处于打印中状态，风扇声和电流声持续数小时。在一个以"太吵"为唯一动机的项目里，用几小时的低噪音换一次性的启动噪音，方向是反的。
  （附带的耗电顾虑实测 50–130W，属可接受范围，不构成独立理由。此路是因噪音出局，不是因功耗。）

---

## 输入 → 处理 → 输出

- **输入**：一个已切好的任务文件（3mf/gcode）+ 一个绝对时刻（如今晚 23:30）
- **输出**：到点后打印机开始打印；期间产生一条可回溯的日志记录
- **中间发生了什么**：
  1. 服务接收任务，**持久化**（关键：不是内存里挂 timer）
  2. 静默等待。此阶段打印机对该任务一无所知——不预热、不转风扇、不出声
  3. 到点，检查打印机状态
  4. 空闲 → 通过传输层 adapter 下发并启动；非空闲 → 按配置处理（默认放弃）
  5. 无论成败，写日志

传输层抽象为可插拔 adapter，上层调度不关心底下走的是哪条通道。

---

## 最小闭环

> 晚上 8 点，切完一个模型。在 Studio 之外交给服务，指定 23:30。合上电脑离开书房。
>
> 23:30，打印机自己启动，开始打印。在此之前它没发出过任何声音。
>
> 第二天早上，能从日志里看到这个任务几点触发、结果如何。

这就是 v0.1 的验收标准。中途改主意能撤销，也算在内。

## 明确不做

- [ ] 失败/异常推送通知 —— **预留接口，不实现**。摄像头、spaghetti detection 一概不碰
- [ ] 到点机器忙时的重试或排队 —— 默认放弃，可配置，但不做"十分钟后再试"
- [ ] 任务队列、多任务、多打印机
- [ ] 账号、权限、Web UI（单人单机自用）
- [ ] 参与切片。服务只搬运已经切好的文件
- [ ] 云端部署（与本地 MQTT 通道矛盾，需额外内网穿透，不属第一版）
- [ ] 固件逆向（见下方「超出 v0.1 的方向」）

## 已知 / 未知 / 假设

### 已知（定了的）

- 触发时刻是每次单独指定的绝对时间，不是固定作息、也不是"N 小时后"
- 到点直接开打，不需要二次确认
- 任务必须持久化。服务重启、电脑睡眠唤醒之后待发任务要还在——这条把项目从"一个脚本"抬到了"有状态的常驻进程"，是成本影响最大的一条
- 传输层保留 A/B 两种实现，接口先抽象出来
- 日志做最薄一层：append-only 文件，记「发送时间 / 触发时间 / 结果 / 失败原因」。不做查询界面、不做数据库。目的是排查"为什么那晚没打起来"——出问题时人在睡觉，现场什么都看不到
- v0.1 跑在当前这台电脑上。家庭服务器（已购、未装系统）是并行线，不是前置依赖

### 未知（还没想清楚的）

- 任务怎么交给服务。上一轮里 A（改 Studio 加时间输入框）和 C（后处理脚本）都可接受，但 C 已随 `G4` 方案出局，A 需要改 Studio 源码。**"切完片之后到底做什么动作把任务交出去"这一步目前是空的**
- 服务的形态：常驻进程 + CLI？带 systemd unit？没定
- 电脑睡眠期间到点了怎么办（v0.1 跑在会睡眠的机器上，这是个现实问题）
- 提前上传 vs 到点上传（见假设表第 1 条，决定后才能定架构）

### 假设（拍脑袋定的，没验证过）⚠️

| 假设 | 如果它是错的会怎样 | 验证成本 |
|---|---|---|
| 把文件传到打印机存储、但不发启动指令，机器保持完全静默 | 架构从"提前传+到点发指令"翻转为"到点才传"。大文件上传耗时与失败风险全部压进触发时刻，容错设计要重做 | 10 分钟，手动操作，不写代码 |
| A1 能切到 LAN Only 模式，且 FTPS 能用 IP+访问码连上 | 通道 A 整条不成立，只剩踩红线的通道 B | 20 分钟，手动 |
| LAN 模式的本地 MQTT 提供了"从机器存储启动指定文件"的指令，且现固件未加签名限制 | 通道 A 只能传文件不能启动，等于废掉。回退到 B | 2–4 小时抓包 |
| 打印机的空闲/忙状态能从 MQTT 上报字段直接读到 | "机器忙则放弃"这条逻辑没有判据，只能盲发 | 30 分钟（承接上条） |
| 通道 B（模拟 Studio 走云）在当前签名/授权机制下仍可模拟 | A/B 双通道退化成单通道，抗风险能力归零 | 未知，可能数天 |
| 1–2 周够用 | 协议逆向的时间高度不可预测，可能卡在认证上两天。超期则 v0.1 缩水到"只跑通一条通道、无 adapter 抽象" | —— |

## 资源约束

- **时间**：1–2 周
- **可复用**：
  - 家庭服务器（已购，未装系统，与本项目同步推进）
  - 功率计（已有，本轮已用它测出 50–130W）
  - 现成的 Python/Linux/网络协议基础
- **不可控依赖**：拓竹的传输协议。这是项目里唯一一个"别人说了算、且对方在主动收紧"的环节

---

## 关于两条传输通道

| | A：本地 MQTT + FTPS | B：逆向云 API |
|---|---|---|
| 路径 | 服务器 → 打印机（同内网） | 服务器 → 拓竹云 → 打印机 |
| 依赖 | LAN Only 模式 | 拓竹账号、云可用 |
| 风险 | 手机 App 远程功能受限 | 踩在厂商红线上；固件更新随时可能掐掉 |
| 云端部署 | 不可（需内网穿透） | 可 |
| 优先级 | **v0.1 主线** | 备选，接口留位 |

C（模拟键鼠点 Studio 界面）已排除：要求跑在有图形界面且登录账号的机器上，与"迁到无头服务器"的目标直接冲突。

**一个需要正视的排序问题**：目前的计划是把 A/B 的验证推到后面，先做定时、取消、日志。但那三项是闭着眼睛也能写出来的 CRUD，唯独"发送"这一下不是自己说了算。风险排序上这是反的——先做完调度器再发现两条通道都不通，等于白做。

## 超出 v0.1 的方向（记录，不排期）

- **固件逆向**。已明确表示后续会考虑，个人自用。
  - 事实澄清：AGPL 链条是 Slic3r → PrusaSlicer → Bambu Studio，只覆盖切片器，固件不在这条链上——它闭源不构成对开源许可的违反，与网络插件的争议是两回事。
  - 实际风险在硬件侧而非法律侧：砖机、失保，而 A1 是目前唯一一台机器。
  - 若最终走通，理论上能实现"机器端原生挂起任务"，那是比本项目更彻底的解法。
- 内网穿透 + 云端部署
- 推送通知（接口已预留）

## 下一步

**一件事：手动验证「传文件到打印机但不启动，机器是否保持完全静默」。**

做法：把 A1 切到 LAN Only 模式，用任意 FTP 客户端把一个 3mf 传到机器存储，然后站在旁边听 + 看功率计。

选它的理由：

- 它是整个项目的**地基假设**。"打印机在触发前一无所知"是本项目唯一的存在理由，如果上传动作本身就会唤醒机器发出声音，那 v0.1 的架构从第一天就是错的
- 10 分钟，不写一行代码
- 顺带把假设表第 2 条（LAN Only + FTPS 连通性）也验了

**不要先动手写调度器。** 它是这个项目里最不需要担心的部分。
